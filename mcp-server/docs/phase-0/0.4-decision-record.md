## 2. D2 — Scope: everything in Kanvaro, in three waves

**Instruction:** everything that can be done in the existing Kanvaro system, reads and
writes, is in release 1. Critical writes may come last.

**Proposal:** build and release in three waves inside release 1. Every wave has its own
role tests before the next starts.

- **Wave 1 — Reads.** Every module, read-only.
- **Wave 2 — Everyday writes.** Create and update the normal work items.
- **Wave 3 — Critical writes.** Anything that:
  - deletes data;
  - closes or reopens a workflow (sprint start or complete, stand-up complete or reopen, approvals);
  - changes money (budget, expenses, income, rates);
  - changes who can access what (team membership, invitations, roles, user roles);
  - changes organisation-wide settings;
  - runs in bulk (bulk update, CSV import, sync).

### 2.2 How many tools

Kanvaro has about 270 routes. One tool per route would give AI clients a list too long to
choose from reliably. **Proposal (D4):** one read tool and one or two write tools per
module area, with an `action` field for related operations. For example,
`task_update` covers update, assign and status change. That gives roughly **45–55 tools**.
The exact list is task 0.6.

### 2.3 Rules every write tool follows

These apply whatever wave a tool is in. The reasons are in the Kanvaro review.

- **Field allow-list.** Each tool sends only the fields in its schema. Several Kanvaro
  routes save whatever body they receive.
- **Response filter.** Each tool copies across only the fields the AI needs. Some routes
  return pay rates and password-reset values.
- **The server sets the limits.** It always sends its own page size and never relies on
  Kanvaro's defaults (up to 10,000 rows).
- **No moving tasks between projects** in the update tool. Kanvaro does not check access to the
  target project.

### 2.4 D3 — Never exposed

Not user actions, or too sensitive to hand to an AI client:

| Routes | Reason |
|---|---|
| `auth/*` (login, logout, refresh, password reset, OTP) | Sign-in happens only on Kanvaro's page |
| `settings/security/password`, deleting your own account (`profile` DELETE) | Account security; never by an AI |
| `setup/*`, `debug/*`, `cron/*`, `test-connection`, `test-email`, `email` | System administration and internals |
| `settings/database`, `settings/email` | Server configuration and credentials |
| `members/accept`, `members/validate-invitation` | Used by the invited person, not a signed-in user |
| `realtime`, `notifications/stream`, `notifications/subscribe`, `notifications/test` | Browser connections, not actions |
| `uploads/*` (raw files), `landing-page`, `contact`, `feedback`, `openapi` | Not project data |
| Report **exports** (`*/export`) | Return files; the matching read tool returns the same data |

## 4. Other decisions

### D5 — Confirmation for critical writes

Each wave-3 tool works in two calls:
1. The first call returns a summary ("Delete task PRJ-42 'Fix login', 3 comments")
   and a one-time confirmation code valid for 5 minutes.
2. The second call must repeat that code.

The audit log records both calls. Clients such as Claude Code also ask the user before
each tool call. Our check is a second layer that doesn't depend on the client.

### D6 — Client registration

**Proposed:** approved clients are pre-registered by an admin. Claude Code is added
with:

```
claude mcp add --transport http --client-id kanvaro-claude-code --callback-port 33418 kanvaro <server URL>
```

This was tested in 0.3. It needs no fetching of client documents and no outbound
internet, and matches return addresses exactly. Client metadata documents (also tested
and working) can be added later for clients we don't control.

### D7 — Where the server runs

**Proposed:** company network or VPN for release 1. Claude Code runs on the user's
machine, so that is enough. A public address (needed only for Claude on the web) can
come after release 1, with a security review.

### D8 — Audit log retention

**Proposed:** 180 days for all entries. Change this if company policy needs longer for
writes (for example 1 year).

### D9 — Single-tenant

Kanvaro creates one organisation per installation, and its own developer guide says it is
single-tenant. Remove "two organisations" from task 0.7 and the test plan. Cross-project
access tests stay.
