# Task 0.2 — MCP TypeScript SDK: support and decision

**Status:** decided, 20 Nov 2026 (to be confirmed by the supervisor in task 0.4)
**Checked against:** the published npm packages (downloaded and inspected), the SDK
repository, its v2 documentation and release notes.

---

## Decision

1. **Use the official SDK v2** for the MCP endpoint, the 2026-07-28 protocol, bearer-token
   checking and the discovery (metadata) responses.
2. **Write the authorization server ourselves** (authorize, consent, Kanvaro callback,
   token, revoke). The SDK no longer provides one for new servers.
3. **Runtime:** Node 24 LTS (supported to April 2028; Node 20 is end of life and Node 22
   ends April 2027), TypeScript, Express 5, Zod 4.

## Does it support revision 2026-07-28?

**Yes, as an opt-in.**

- `@modelcontextprotocol/core` 2.4.0 defines `FIRST_MODERN_PROTOCOL_VERSION = '2026-07-28'`.
- The default `LATEST_PROTOCOL_VERSION` is still `2025-11-25`; a server speaks
  2026-07-28 only when built with `createMcpHandler` (SDK guide: "support-2026-07-28").
- The SDK handles `server/discover`, the per-request `_meta`, the protocol headers and
  older clients.
- Claude Code negotiates 2026-07-28 when offered, otherwise uses the 2025 protocol.

## OAuth helpers: what the SDK gives and what it doesn't

| Need | SDK v2 | We build |
|---|---|---|
| Bearer check on `/mcp` (401/403 + `WWW-Authenticate`) | ✅ `requireBearerAuth` (express) / `verifyBearerToken` (server) | the `verifyAccessToken` function (look up the token hash in our DB) |
| Audience check | ✅ `expectedResource` option — **off unless set**; our verifier must fill `AuthInfo.resource` | set it in config |
| Expiry check | ✅ rejects tokens without an expiry or past it | return `expiresAt` from the verifier |
| Scope check / step-up | ✅ `requiredScopes`, `requireScopes` | — |
| Protected resource + authorization server metadata | ✅ `mcpAuthMetadataRouter`, `getOAuthProtectedResourceMetadataUrl` | metadata values (0.1 §2) |
| `Origin` / `Host` validation | ✅ `originValidation`, `hostHeaderValidation` | allowed origins in config |
| Authorize, consent, callback, token, revoke | ❌ only in `server-legacy` (frozen); guide: *"Use a dedicated identity provider for new servers"* | **all of it** |
| CIMD fetching | ❌ not provided | later, if needed |
| Dynamic registration | ❌ legacy only | not in release 1 |
| Proxy to an upstream server | ⚠️ legacy `ProxyOAuthServerProvider` returns the upstream's tokens to the client | **not used** — it would pass Kanvaro tokens to Claude Code, which the spec forbids |

### Why not a third-party identity provider?

The spec allows one, but sign-in must happen on **Kanvaro's** login page and the MCP
server must hold each user's Kanvaro token. An external identity provider would add a
second system between them without removing any work. Writing the small
authorization server is simpler.

## How we write the authorization server (kept small)

- **Opaque tokens, not JWTs.** Random 32-byte values; only the SHA-256 hash is stored
  (`tokens` collection). The verifier looks up the hash. No signing keys to manage or
  rotate.
- **PKCE:** Node `crypto` (`sha256`, base64url) — about 10 lines.
- **Codes:** random, hashed, 60-second expiry, single use (atomic `findOneAndUpdate`).
- **No new OAuth library needed.** If one is wanted later, `oauth4webapi` covers the
  client side toward Kanvaro.
- Estimated size: authorize + consent + callback + token + revoke in roughly 5 route
  files plus a token store.
