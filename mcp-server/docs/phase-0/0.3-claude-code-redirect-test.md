# Task 0.3 — How Claude Code handles localhost return addresses

**Status:** done, 20 Nov 2026
**Tested with:** Claude Code 2.1.325 (VS Code extension, Windows) against a test
authorization server that records every request
([tools/oauth-probe.mjs](../../tools/oauth-probe.mjs)).

---

## 1. The rule (result of this task)

The MCP server compares return addresses (`redirect_uri`) **exactly**, with one exception:

> **Loopback exception.** If the registered address uses `http` and the host
> `localhost`, `127.0.0.1` or `[::1]`, the requested address may differ from it **only
> in the port**. Scheme, host (as written), path and query must match exactly.
> The exception never applies to any other host or to `https` addresses.

This is the rule in RFC 8252 §7.3 and RFC 9700 §4.1.3, which the CIMD draft (§4.2)
refers to. Any address that fails the check gets an error page and **no redirect**.

**Why the exception is needed:** Claude Code's own client metadata document registers
`http://localhost/callback` and `http://127.0.0.1/callback` **without a port**, but every
sign-in uses a random port (e.g. `http://localhost:45816/callback`). Strict matching
would refuse Claude Code every time.

## 3. Findings

### 3.1 Return addresses

| Set-up | `redirect_uri` sent | Registered value | Exact match? |
|---|---|---|---|
| CIMD (A) | `http://localhost:45816/callback` (random port) | `http://localhost/callback`, `http://127.0.0.1/callback` (from Claude Code's document) | **No** — port only differs |
| Pre-registered (B) | `http://localhost:8080/callback` | as configured by us | Yes |
| Dynamic registration (C) | `http://localhost:43642/callback` (random port) | same — Claude Code registers the exact port | Yes |

- Host is always `localhost`, never `127.0.0.1` (the docs mention v2.1.229 briefly sent
  `127.0.0.1`). Path is always `/callback`.
- The random port for run A was the same on two attempts for the same server name; do
  not rely on this.

### 3.4 Sign-in and token behaviour (all runs)

| Item | Observed |
|---|---|
| Choice when both CIMD and dynamic registration are offered | CIMD |
| Discovery | `/.well-known/oauth-protected-resource/mcp` then `/.well-known/oauth-authorization-server`; did not try the root or OpenID variants (first ones succeeded) |
| PKCE | `S256` always; verifier correct |
| `state` | Always sent |
| `scope` | `kanvaro` (taken from the 401 challenge / metadata) |
| `resource` | Sent in the authorize request, the code exchange **and every refresh**; value = the MCP URL exactly |
| Client authentication | None (public client): no `Authorization` header, `client_id` in the form body |
| `iss` in the redirect | Accepted when correct (wrong `iss` not tested; docs say it is rejected) |
| Refresh token rotation | Works: each refresh used the newest token |
| Refresh timing | With a **30-second** access token Claude Code refreshed **before every request**. With **15 minutes**: no refreshes. Access tokens must be well above Claude Code's refresh margin |

### 3.5 MCP protocol behaviour

- First request is `server/discover` with `MCP-Protocol-Version: 2026-07-28`,
  `Mcp-Method: server/discover` and `_meta` (protocol version, client info,
  capabilities). No `Mcp-Session-Id`.
- The test server answered "method not found", and Claude Code **fell back** to
  `initialize` with protocol `2025-11-25`, then opened `GET /mcp` (405 accepted), then
  `tools/list`. Both protocol paths work.
- Before sign-in, Claude Code's first request carried no token and got the 401 with
  `resource_metadata`, which started discovery as expected.

### 3.6 Not tested

- Rejection of a wrong `iss` (documented by Claude Code; low risk).
- Two refreshes at the same time (needs the real server's per-user lock).
- Token revocation on `claude mcp logout` (the test server had no revocation endpoint).
- Claude Code on macOS/Linux (behaviour should be the same; not verified).

## 4. Effect on the plan

| Item | Decision / change |
|---|---|
| Rule for return addresses (3.4, K-2) | Exact match plus the loopback exception in §1. Test cases: same port ✓, other port on `localhost` ✓, `127.0.0.1` vs `localhost` ✗, other path ✗, `https://localhost:x` ✗, any non-loopback host with another port ✗ |
| Registration choice (0.4) | All three work. **Pre-registered** is still the simplest (no fetching, no outbound internet, exact match). Users add the server with `claude mcp add --transport http --client-id kanvaro-claude-code --callback-port <port> kanvaro <url>` |
| Callback port | Avoid 8080 (often in use, and Claude Code must bind it locally). Pick an unusual fixed port, e.g. **33418**, and document it |
| CIMD, if enabled | Must apply the loopback exception; needs outbound access to `https://claude.ai` |
| MCP access token lifetime (3.6) | **15 minutes.** Short lifetimes cause a refresh before every call |
| Refresh token (3.6) | Rotation confirmed compatible; keep it |
| `resource` / audience (3.6, 3.7) | Claude Code sends the exact MCP URL; the server stores it as the audience and checks it with `expectedResource` |
| 1.8 acceptance | Claude Code tries 2026-07-28 first; the SDK's `createMcpHandler` should answer `server/discover` so the new protocol is used |
| Kanvaro side (K-2) | Kanvaro's authorize page only ever redirects to the MCP server's callback (one fixed HTTPS address), so Kanvaro needs **no** loopback exception |

## 5. How to rerun (after a Claude Code update)

```bash
# terminal 1 — test server (MODE=all | dcr | cimd)
MODE=all node mcp-server/tools/oauth-probe.mjs

# terminal 2 — in an interactive terminal
claude mcp add --scope local --transport http probe http://localhost:8790/mcp
claude mcp login probe          # browser opens; the probe approves automatically
claude mcp list
claude mcp logout probe && claude mcp remove --scope local probe
```

Results are written to `log-<mode>.jsonl` next to the script.
The probe is a test tool only: it approves every request and does not block private
addresses when fetching metadata.
