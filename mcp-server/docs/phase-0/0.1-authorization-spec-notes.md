# Task 0.1 — MCP authorization: required endpoints and fields

**Status:** done, 20 Nov 2026
**Sources:** MCP specification revision 2026-07-28 (authorization, client registration,
authorization server discovery, security considerations, Streamable HTTP, changelog);
IETF draft-ietf-oauth-client-id-metadata-document-03 (2 Nov 2026); Claude Code MCP
documentation. Links at the end.

Keywords MUST / SHOULD / MAY are quoted from the source.

---

## 1. Summary

The MCP server is both the **resource server** (the MCP endpoint) and the
**authorization server** (sign-in for client applications). It is also an OAuth
**client** of Kanvaro. The spec requires:

| # | What | Level |
|---|---|---|
| 1 | Protected resource metadata (RFC 9728) naming our authorization server | MUST |
| 2 | Authorization server metadata (RFC 8414) with `S256` listed | MUST (clients refuse without it) |
| 3 | PKCE S256, exact redirect URI match, HTTPS or localhost redirect URIs | MUST |
| 4 | Tokens bound to this server (`resource` → audience) and checked on every request | MUST |
| 5 | Never pass the client's token to Kanvaro | MUST NOT |
| 6 | User consent per dynamically registered client before sending the user to Kanvaro | MUST |
| 7 | `iss` in the authorization response (RFC 9207) | SHOULD (MCP); MUST in the CIMD draft |
| 8 | Refresh token rotation for public clients | MUST |
| 9 | Client ID Metadata Documents (CIMD); dynamic registration is **deprecated** | SHOULD / MAY |

## 2. Endpoints the MCP server must expose

Assume the MCP endpoint is `https://mcp.example.com/mcp` and the issuer is
`https://mcp.example.com` (no path — keeps discovery to two URLs).

| Endpoint | Path (proposal) | Purpose |
|---|---|---|
| MCP endpoint | `POST /mcp` | Tool calls. `GET`/`DELETE` → 405. |
| Protected resource metadata | `GET /.well-known/oauth-protected-resource/mcp` **and** `GET /.well-known/oauth-protected-resource` | Clients try the path-suffixed URL first, then the root. Serve both. |
| Authorization server metadata | `GET /.well-known/oauth-authorization-server` | Also serve `/.well-known/openid-configuration` with the same body (clients try it second). |
| Authorize | `GET /authorize` | Validates the request, shows consent, redirects to Kanvaro. |
| Kanvaro callback | `GET /callback/kanvaro` | Receives Kanvaro's code; swaps it; redirects to the client. |
| Token | `POST /token` | `authorization_code` and `refresh_token` grants. |
| Registration (optional) | `POST /register` | Dynamic registration — deprecated; keep only if a client needs it. |
| Revoke (optional) | `POST /revoke` | Disconnect (task 3.9). |
| Health | `GET /health` | Monitoring. |

### 2.1 Protected resource metadata

```json
{
  "resource": "https://mcp.example.com/mcp",
  "authorization_servers": ["https://mcp.example.com"],
  "scopes_supported": ["kanvaro"],
  "bearer_methods_supported": ["header"]
}
```

- `authorization_servers` MUST have at least one entry.
- `resource` is the canonical server URI: lowercase scheme and host, no fragment, no
  trailing slash. The same string is the token audience.
- Do **not** list `offline_access` in `scopes_supported` (SHOULD NOT).

### 2.2 401 / 403 responses on the MCP endpoint

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource/mcp", scope="kanvaro"

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="kanvaro", resource_metadata="..."
```

- Missing or invalid token → 401 (MUST). Include `resource_metadata` on every 401.
- Claude Code starts sign-in on any 401 or 403.
- Tokens MUST NOT be accepted in the query string.

### 2.3 Authorization server metadata

```json
{
  "issuer": "https://mcp.example.com",
  "authorization_endpoint": "https://mcp.example.com/authorize",
  "token_endpoint": "https://mcp.example.com/token",
  "revocation_endpoint": "https://mcp.example.com/revoke",
  "response_types_supported": ["code"],
  "grant_types_supported": ["authorization_code", "refresh_token"],
  "code_challenge_methods_supported": ["S256"],
  "token_endpoint_auth_methods_supported": ["none"],
  "scopes_supported": ["kanvaro"],
  "client_id_metadata_document_supported": true,
  "authorization_response_iss_parameter_supported": true
}
```

- `issuer` MUST be identical to the URL the client derived it from (no trailing slash —
  see SDK issue #3186).
- Missing `code_challenge_methods_supported` → clients MUST refuse to continue.
- If `iss` is sent in responses, `authorization_response_iss_parameter_supported` MUST be `true`.
- Add `registration_endpoint` only if dynamic registration is kept.
- All endpoints MUST be HTTPS.

## 3. Client registration

Clients try, in this order (SHOULD): pre-registered details → CIMD (if
`client_id_metadata_document_supported`) → dynamic registration (if
`registration_endpoint`) → ask the user.

### 3.1 Option A — pre-registered clients (simplest)

An admin adds each approved client (ID, name, exact redirect URIs) to configuration.
Claude Code supports this:

```
claude mcp add --transport http --client-id kanvaro-claude-code --callback-port 8080 \
  kanvaro https://mcp.example.com/mcp
```

Redirect URI is then exactly `http://localhost:8080/callback`. No fetching, no SSRF
surface, no registration endpoint.

### 3.2 Option B — Client ID Metadata Documents (CIMD)

The client sends an HTTPS URL as `client_id`; the server fetches a JSON document from it.
Claude Code documents CIMD support but **not its client_id URL**, so this must be tested
(task 0.3).

**The client_id URL** (draft §3): MUST be `https`; MUST have a path other than `/`;
MUST NOT contain userinfo, fragment, or `.`/`..` segments; SHOULD NOT have a query.
Compare by exact string, MUST NOT normalise. SHOULD reject a client_id equal to our own
issuer.

**The document** (draft §4): MUST contain `client_id` (equal to the URL, exact),
`client_name`, `redirect_uris`. MUST NOT contain `client_secret` or any shared-secret
auth method. If no auth method is given, assume `none`; reject client authentication
with `invalid_client`.

**Fetching** (draft §6, §10, §11):

| Rule | Level |
|---|---|
| Do not fetch URLs that resolve to special-use addresses (RFC 6890: private, loopback, link-local, etc.) — check the **resolved IP**, and connect to that IP (prevents DNS rebinding) | MUST NOT (rebinding handling is our choice) |
| Do not follow redirects | MUST NOT |
| Only `200 OK` is success | MUST |
| Read at most **5 KB**; larger is an error | SHOULD |
| `Accept: application/json`; send no cookies or user data | SHOULD |
| Respect `Cache-Control`, with our own min and max cache time; never cache errors | SHOULD / MUST NOT |
| Timeout: not specified — use 5 s | our choice |
| On failure at `/authorize`: show an error page, never redirect | MUST NOT redirect |

**Deployment consequence:** with CIMD the MCP server needs **outbound internet access**
to fetch client documents (for Claude Code, a URL on Anthropic's domain).

### 3.3 Option C — dynamic registration (RFC 7591)

Deprecated in 2026-07-28; MAY support for older clients. Clients MUST send
`application_type` (`native` for Claude Code). Returns a client ID; no fetching.

### 3.4 Recommendation

Release 1: **Option A** (pre-registered, fixed callback port). Add CIMD later if
clients we don't control must connect. This removes task 3.3's fetcher and its SSRF
tests. To be agreed in task 0.4.

## 4. Sign-in flow requirements

| Requirement | Level | Source |
|---|---|---|
| PKCE with `S256`; reject `plain` or missing challenge | MUST | security considerations |
| `state` round-trips unchanged | SHOULD (client); we always echo it | security considerations |
| Redirect URI exact match against registered values (string comparison) | MUST | security considerations; CIMD §4.2 |
| Loopback redirect URIs may use any port (RFC 9700 §4.1.3) | allowed | CIMD §4.2 |
| Redirect URIs must be `localhost` or HTTPS | MUST | security considerations |
| Invalid client or redirect URI → error page, never redirect | MUST | security considerations |
| Client sends `resource` in authorize and token requests; we put it into the token audience and reject a mismatch | MUST | authorization §Resource Parameter |
| `iss` in the redirect back to the client (and on errors) | SHOULD; MUST per CIMD §7 | authorization §Response Validation |
| Consent screen per client before redirecting to Kanvaro; show the client_id hostname and redirect host | MUST (dynamic clients); SHOULD (hostname) | security §Confused Deputy; CIMD §10.6 |
| Short-lived access tokens | SHOULD | security considerations |
| Rotate refresh tokens for public clients | MUST | authorization §Refresh Tokens |
| Do not pass the client's token upstream | MUST NOT | security §Token Passthrough |

**Loopback port rule (input to task 0.3):** exact match by default. If Claude Code uses a
random port (its default), accept `http://localhost:<any port>/callback` **only** when the
registered URI is a loopback URI and only the port differs. With `--callback-port` the
issue disappears.

**Token lifetimes (proposal):** MCP access token 15 min; MCP refresh token ≤ 7 days and
never longer than the stored Kanvaro refresh token.

## 5. Transport changes in 2026-07-28 (affect Phase 1)

| Change | Effect on task |
|---|---|
| No sessions: no `Mcp-Session-Id`, no `initialize` handshake; version and capabilities in each request's `_meta` | 1.8 acceptance is "`server/discover` and one tool call work", not "handshake" |
| `server/discover` MUST be implemented | Provided by the SDK |
| Every POST carries `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`; header must match `_meta` (else 400) | Provided by the SDK |
| Server MUST validate `Origin` and return 403 for invalid values | Use the SDK's `originValidation` |
| No resumable streams (`Last-Event-ID`); a broken stream loses the request | No server state needed |
| `GET`/`DELETE` on the MCP endpoint → 405 | Provided by the SDK |

Claude Code negotiates 2026-07-28 when the server supports it and falls back to the
2025 protocol otherwise, so supporting both is cheap via the SDK.

## 6. Claude Code as a client (documented behaviour)

- Discovery: protected resource metadata first, then `/.well-known/oauth-authorization-server`.
- Callback: `http://localhost:PORT/callback`, random port by default; `--callback-port` fixes it.
- Pre-registered client: `--client-id` (public client), optional `--client-secret`
  (prompted, stored in the keychain).
- Supports CIMD and dynamic registration; order and its client_id URL not documented.
- Refreshes tokens automatically and retries once; on refresh failure shows **Re-authenticate**.
- Rejects an authorization response with an unexpected `iss`.
- `claude mcp logout` revokes; `claude mcp remove` does not.
- Not documented: PKCE method, `resource` parameter, token storage — verify in task 0.3.
- **Verified in task 0.3:** S256, `resource` on every request, CIMD client_id
  `https://claude.ai/oauth/claude-code-client-metadata` with port-less loopback
  redirect URIs (needs the loopback port exception). See
  [0.3-claude-code-redirect-test.md](0.3-claude-code-redirect-test.md).
